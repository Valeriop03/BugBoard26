## Ripetere Le Verifiche

Dalla radice, con Docker e .NET SDK 10 disponibili:

```powershell
docker compose -p bugboard26-tests -f backend/BugBoard26.Tests/docker-compose.tests.yml up -d --wait
dotnet test backend/BugBoard26.slnx
& ./quality/analyze-backend.ps1 -Mode Coverage
```

Per l'analisi completa, configurare SONAR_PROJECT_KEY e SONAR_TOKEN soltanto
nella sessione locale e avviare il server. Sul PC corrente il wrapper
DPAPI esterno alla repository carica il token senza esporlo:

```powershell
& "$env:LOCALAPPDATA/BugBoard26/quality-local/start-sonar.ps1"
& "$env:LOCALAPPDATA/BugBoard26/quality-local/analyze.ps1" -Repository (Get-Location).Path
```

Il wrapper non fa parte del pacchetto sorgente: su un altro PC seguire
`qualita_backend.md` e usare lo script quality esistente. Attendere anche
Compute Engine e Quality Gate, non fermarsi al solo invio dello scanner.
Non pubblicare token, file DPAPI, credenziali locali o file `.env`.

Dalla cartella frontend:

```powershell
npm run build
$env:CHROME_BIN = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
node node_modules/@angular/cli/bin/ng.js test --watch=false --browsers=ChromeHeadless
```

Per una verifica manuale avviare Compose e Angular come nel README;
provare creazione con immagine, suggerimento, dettaglio, risoluzione come
assegnatario, notifica al creatore e lettura USER/ADMIN. Come READONLY:
lista/dettaglio/notifiche leggibili, niente creazione, stato o lettura
notifica. Come non ADMIN: menu Utenti assente e `/users` reindirizza.
Usare dati sintetici riconoscibili, non modificare quelli preesistenti.
Il collaudo automatico temporaneo non e' un nuovo framework E2E versionato;
le sue evidenze e i passi manuali sono conservati senza credenziali.

## Per La Discussione

Il frontend e l'API sono separati, e le autorizzazioni decisive restano sul
server. I DTO impediscono input fuori contratto senza introdurre una nuova
architettura. I test HTTP usano PostgreSQL reale per verificare insieme
JWT, permessi, query e persistenza. Il cambio stato salva issue e notifica
nello stesso salvataggio EF, e il ripetuto RESOLVED non duplica l'evento.
Coverage e Sonar descrivono verifiche misurate, non un prodotto senza limiti.
Le prove con persone rimangono un'attivita' diversa dai test automatici.

- **Perche' non InMemory?** Le query usano anche ILike PostgreSQL: servono
  provider e vincoli reali.
- **Perche' validare gli enum?** Il JSON numerico puo' contenere interi
  non definiti; EnumDataType li rifiuta prima del controller.
- **Basta nascondere Utenti?** No: guard e API proteggono anche accessi diretti.
- **93,7% significa tutto corretto?** No: misura copertura, non correttezza
  assoluta o usabilita'.
- **READONLY puo' segnare letta?** No, per RF-17 concordato dal gruppo;
  puo' soltanto consultare le proprie notifiche.
- **Che cosa manca ancora?** Evidenze umane, CASE e rehearsal, poi release
  e consegna manuali, non nuove funzioni inventate.

Comandi Git solo proposti: vedere `../consegna.md`. Prima controllare diff,
file nuovi e report, senza aggiungere segreti o dipendenze generate.
