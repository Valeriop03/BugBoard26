\section{Introduzione}

Il presente documento descrive la progettazione del sistema BugBoard26, realizzato come applicazione distribuita per la gestione collaborativa di issue in progetti software.

Il documento rappresenta la seconda fase del lavoro progettuale e riprende quanto definito nella specifica dei requisiti. In particolare, vengono descritte le scelte architetturali, la suddivisione delle responsabilità tra frontend, backend e database, la struttura principale delle classi di design e le motivazioni delle principali scelte tecnologiche.

Le funzionalità considerate sono quelle assegnate al gruppo:

\begin{itemize}
    \item autenticazione tramite email e password;
    \item creazione di utenti da parte degli amministratori;
    \item creazione di issue da parte di ADMIN e USER autenticati;
    \item visualizzazione, ricerca, filtro e ordinamento delle issue;
    \item cambio stato delle issue assegnate;
    \item notifica al segnalatore quando una issue viene risolta;
    \item esportazione delle issue in formato CSV;
    \item archiviazione delle issue da parte degli amministratori;
    \item suggerimento automatico dello assegnatario in base al carico di lavoro;
    \item gestione di utenti readonly;
    \item contrassegno di una issue come duplicata.
\end{itemize}

\section{Obiettivi di progettazione}

La progettazione del sistema è stata guidata dai seguenti obiettivi:

\begin{itemize}
    \item separare chiaramente frontend, backend e persistenza;
    \item mantenere il backend indipendente dalla tecnologia utilizzata per la interfaccia utente;
    \item esporre le funzionalità tramite API REST;
    \item centralizzare la logica applicativa nel backend;
    \item distinguere controller, regole di dominio e persistenza tramite Entity Framework Core;
    \item limitare la complessità, mantenendo il sistema coerente con il lavoro di un gruppo di tre studenti;
    \item rendere il progetto facilmente testabile, estendibile e spiegabile in sede di discussione.
\end{itemize}

\section{Architettura generale}

Il sistema è stato progettato come applicazione web distribuita composta da tre macro componenti:

\begin{itemize}
    \item \textbf{Frontend Angular}, responsabile della interfaccia utente e della interazione con lo utente;
    \item \textbf{Backend ASP.NET Core Web API}, responsabile della logica applicativa, della autenticazione, della gestione dei ruoli e della esposizione delle API REST;
    \item \textbf{Database PostgreSQL}, responsabile della persistenza dei dati.
\end{itemize}

La comunicazione tra frontend e backend avviene esclusivamente tramite richieste HTTP verso API REST. Le richieste protette includono un token JWT generato dal backend durante la fase di login.

Questa scelta permette di rispettare il vincolo di separazione tra frontend e backend: il backend non dipende da Angular e potrebbe essere utilizzato anche da una diversa interfaccia, per esempio una applicazione mobile o desktop.

\section{Scelte tecnologiche}

\subsection{Frontend Angular}

Angular è stato scelto per realizzare una Single Page Application strutturata in componenti. Questa tecnologia permette di separare la presentazione dalla logica di accesso alle API e offre strumenti già integrati per routing, form, servizi e gestione delle chiamate HTTP.

Nel frontend sono previsti componenti dedicati alle principali schermate:

\begin{itemize}
    \item login;
    \item lista issue;
    \item creazione issue;
    \item dettaglio issue;
    \item archivio issue;
    \item notifiche;
    \item gestione utenti per amministratori.
\end{itemize}

\subsection{Backend ASP.NET Core Web API}

ASP.NET Core Web API è stato scelto per il backend perché supporta in modo nativo la creazione di API REST, la gestione della dependency injection, la autenticazione JWT e la integrazione con Entity Framework Core.

La struttura implementata distingue:

\begin{itemize}
    \item \textbf{Controller}: validano richieste, applicano autorizzazioni, interrogano il contesto e restituiscono DTO;
    \item \textbf{IssueDomainService}: verifica i permessi di cambio stato e calcola il suggerimento dell'assegnatario;
    \item \textbf{ApplicationDbContext}: mappa entità e relazioni e salva le modifiche tramite Entity Framework Core;
    \item \textbf{Servizi di autenticazione}: \texttt{Pbkdf2PasswordHasher} e \texttt{JwtTokenService}, con le rispettive interfacce.
\end{itemize}

Questa struttura consente di separare le responsabilità e rende più semplice testare la logica applicativa.

\subsection{Database PostgreSQL}

PostgreSQL è stato scelto come database relazionale per la persistenza delle informazioni principali del sistema. Le entità principali sono utenti, issue e notifiche.

La scelta di un database relazionale è coerente con la natura dei dati, che presentano relazioni chiare tra utenti, issue e notifiche.

\subsection{Autenticazione JWT}

La autenticazione è basata su token JWT. Dopo il login, il backend restituisce un token contenente le informazioni essenziali dello utente, tra cui identificativo e ruolo. Il frontend invia il token nelle richieste successive verso le API protette.

Questa soluzione permette di mantenere il backend stateless rispetto alle sessioni e di gestire in modo semplice autorizzazioni basate sui ruoli.

\section{Organizzazione del backend}

Il backend è stato progettato separando le responsabilità in più livelli.

\subsection{Controller}

I controller rappresentano il punto di ingresso delle richieste HTTP. Ogni controller espone un gruppo di API legate a una specifica area funzionale:

\begin{itemize}
    \item \texttt{AuthController}: login e generazione del token JWT;
    \item \texttt{UsersController}: creazione e consultazione degli utenti;
    \item \texttt{IssuesController}: creazione, ricerca, filtro, cambio stato, archiviazione, duplicati ed export;
    \item \path{NotificationsController}: consultazione e lettura delle notifiche.
\end{itemize}

\subsection{Servizi applicativi}

\texttt{IssueDomainService} lavora su oggetti del dominio, senza dipendere dal database. Espone \texttt{CanChangeIssueStatus}, \texttt{SuggestAssignee} e \texttt{SearchIssues}. La ricerca API usa invece \texttt{ILike} nelle query di \texttt{IssuesController}; l'export CSV è costruito nello stesso controller. Il controller aggiorna stato e date, aggiunge la notifica e chiama \texttt{SaveChangesAsync}. Non esistono \texttt{IssueService}, \texttt{NotificationService} o repository nel codice attuale.

\subsection{DbContext}

\path{ApplicationDbContext} rappresenta il punto di integrazione con Entity Framework Core e PostgreSQL. Configura indici, lunghezze dei campi, conversioni degli enum e relazioni. Espone i \texttt{DbSet}:

\begin{itemize}
    \item \texttt{Users};
    \item \texttt{Issues};
    \item \texttt{Notifications}.
\end{itemize}

\texttt{Program.cs} chiama \texttt{DatabaseSeeder.SeedAdminAsync} prima di accettare richieste. Il seeder esegue \texttt{Database.MigrateAsync()} e crea un admin attivo solo se manca un utente di ruolo ADMIN. Le migrazioni presenti sono in \path{backend/BugBoard26.Api/Migrations}; non serve una seconda procedura manuale per applicarle. Connessione, JWT e credenziali iniziali sono configurabili tramite variabili d'ambiente.

\section{Principali scelte di design}

\subsection{Separazione frontend e backend}

Il frontend non accede direttamente al database e non contiene logica di business critica. Tutte le regole principali, come controllo dei ruoli, cambio stato, archiviazione e gestione dei duplicati, sono implementate nel backend.

\subsection{Uso di servizi applicativi}

Le regole pure di \texttt{IssueDomainService} sono verificabili senza database. Le operazioni persistenti restano nei controller e sono verificate con richieste HTTP e PostgreSQL nei test di integrazione.

\subsection{Accesso ai dati}

I controller ricevono \path{ApplicationDbContext} tramite dependency injection. Le query di consultazione usano \texttt{AsNoTracking}; le operazioni di modifica lavorano sulle entità tracciate e chiamano \texttt{SaveChangesAsync}. Non viene introdotto un livello repository aggiuntivo.

\subsection{Gestione dei ruoli}

Il sistema prevede tre ruoli principali:

\begin{itemize}
    \item \texttt{ADMIN}: può gestire utenti, creare issue, cambiare stato, archiviare e contrassegnare duplicati;
    \item \texttt{USER}: può creare issue, consultarle e cambiare lo stato delle issue assegnate;
    \item \texttt{READONLY}: può consultare le issue, senza crearle o modificarle.
\end{itemize}

Il controllo dei ruoli viene effettuato lato backend, in modo da impedire operazioni non autorizzate anche in caso di manipolazione della interfaccia frontend.

Lista, dettaglio, archivio, ricerca ed export CSV sono accessibili a tutti e tre i ruoli autenticati. Nel frontend \texttt{canChangeStatus} mostra il pannello solo ad ADMIN o USER assegnatario; \texttt{canCreateIssue} e \texttt{issueCreationGuard} escludono READONLY dalla creazione, mentre \texttt{adminGuard} protegge la pagina utenti. Riferimenti: \path{frontend/src/app/pages/issue-detail-page/issue-detail-page.component.ts}, \path{frontend/src/app/services/auth.guard.ts} e \path{frontend/src/app/app.routes.ts}.

\paragraph{Requisiti del cambio stato.}
RF-10 e UC-02 consentono l'operazione all'assegnatario oppure all'amministratore; RF-17 esclude readonly dalle modifiche alle issue. RNF-02 richiede il controllo sul backend e RNF-05 richiede che l'interfaccia renda chiare le operazioni disponibili per ruolo.

\paragraph{Comportamento attuale.}
\path{IssuesController.UpdateStatus} espone PATCH \path{/api/issues/{id}/status} per \texttt{ADMIN}, \texttt{USER}. Verifica l'account attivo e chiama \path{IssueDomainService.CanChangeIssueStatus}: admin può agire su qualsiasi issue, USER deve essere assegnatario e READONLY è escluso anche se assegnato. Una richiesta non autorizzata è rifiutata con 403; l'account corrente assente o inattivo produce 401, una issue inesistente 404.

\paragraph{Differenze e verifiche aperte.}
\begin{itemize}
    \item Il frontend propone \texttt{TODO}, \texttt{IN\_PROGRESS}, \texttt{RESOLVED}, \texttt{CLOSED} e disabilita il cambio per una issue \texttt{DUPLICATE}. \texttt{UpdateStatus} non implementa una matrice di transizioni né quel blocco: non va presentata come requisito una sequenza obbligatoria.
    \item \texttt{UpdateStatus} accetta ancora \texttt{Duplicate} senza riferimento all'originale, anche per un USER assegnatario; UC-03 riserva il contrassegno all'admin e richiede l'originale. \texttt{MarkAsDuplicate} conserva l'eventuale \texttt{ResolvedAt}. Questi punti backend restano da verificare dopo il merge delle correzioni del collega: questa revisione documentale non li dichiara risolti e non modifica i requisiti.
\end{itemize}
Riferimenti: \path{backend/BugBoard26.Api/Controllers/IssuesController.cs}, metodi \texttt{UpdateStatus} e \texttt{MarkAsDuplicate}; \path{backend/BugBoard26.Api/Services/IssueDomainService.cs}, metodo \path{CanChangeIssueStatus}.

\subsection{Suggerimento automatico dello assegnatario}

\texttt{IssueDomainService.SuggestAssignee} considera gli utenti attivi non READONLY, inclusi gli ADMIN, e conta le issue non archiviate in stato \texttt{TODO} o \texttt{IN\_PROGRESS}. Sceglie il carico minore e, a parità, l'identificativo utente minore. Questo descrive il criterio implementato, senza assumere un ordinamento per email.

\subsection{Gestione delle notifiche}

\paragraph{Requisito.}
RF-11 richiede la notifica al segnalatore quando la issue passa a \texttt{RESOLVED}. Per la verifica di questo flusso, ogni utente deve consultare e segnare come lette soltanto le proprie notifiche.

\paragraph{Comportamento attuale della risoluzione.}
In \path{IssuesController.UpdateStatus}, se lo stato richiesto differisce dal corrente, vengono aggiornati \texttt{Status} e \texttt{UpdatedAt}. Per \texttt{RESOLVED} viene impostato \texttt{ResolvedAt} in UTC e aggiunta una \texttt{Notification} con \texttt{UserId = CreatedById}, \texttt{IssueId}, messaggio di risoluzione, \texttt{IsRead = false} e \texttt{CreatedAt} in UTC. Una sola chiamata \texttt{SaveChangesAsync} persiste issue e notifica.

La ripetizione dello stato corrente risponde 200 con la issue, senza scritture, date nuove o ulteriori notifiche. Uscendo da \texttt{RESOLVED}, \texttt{ResolvedAt} viene azzerato senza eliminare o cambiare la lettura delle notifiche precedenti. Un nuovo ingresso in \texttt{RESOLVED} imposta una nuova data e crea una nuova notifica. Non è presente un invio email o un aggiornamento in tempo reale della pagina notifiche.

\paragraph{Comportamento attuale delle notifiche.}
\path{NotificationsController.GetAll} restituisce con GET \path{/api/notifications} solo le notifiche con \texttt{UserId} uguale all'utente corrente, dalla più recente. \texttt{MarkAsRead}, PATCH \path{/api/notifications/{id}/read}, verifica il proprietario prima di impostare \texttt{IsRead = true}. Restituisce 403 per la notifica altrui, 404 per un ID inesistente e 401 per account corrente assente o inattivo. Anche ADMIN può operare solo sulle proprie notifiche. Ripetere la lettura di una propria notifica restituisce 200 e mantiene \texttt{IsRead = true}; non esiste un endpoint di dettaglio notifica per ID.

La pagina Angular carica l'elenco all'apertura, evidenzia le notifiche non lette e aggiorna l'elemento con la risposta del PATCH. Il pulsante \emph{Segna come letta} è mostrato solo per notifiche non lette. Il dettaglio issue visualizza \texttt{ResolvedAt}; \texttt{IssuesService} converte i nomi di stato Angular nei nomi API, ad esempio \texttt{RESOLVED} in \texttt{Resolved}.

Riferimenti: \path{backend/BugBoard26.Api/Controllers/NotificationsController.cs}; modelli \path{backend/BugBoard26.Api/Models/Issue.cs} e \path{backend/BugBoard26.Api/Models/Notification.cs}; pagine \path{frontend/src/app/pages/notifications-page/notifications-page.component.ts} e relativo HTML; \path{frontend/src/app/services/notifications.service.ts}.

\paragraph{Differenza da chiarire.}
RF-17 parla di readonly \emph{senza modificare dati}, mentre il design circoscrive il divieto alle issue. \texttt{NotificationsController.MarkAsRead} e la pagina notifiche non escludono READONLY: un account attivo di questo ruolo può segnare come letta una propria notifica. Se RF-17 vieta anche questa scrittura, il codice non è conforme; se il divieto riguarda solo le issue, il requisito va chiarito con il committente. RF-17 resta invariato e non si assume una nuova eccezione.

\subsection{Gestione dei duplicati}

Solo gli amministratori possono contrassegnare una issue come duplicata. Quando questo avviene, la issue viene collegata a una issue principale e il suo stato viene impostato a \texttt{DUPLICATE}. In questo modo rimane tracciabile ma non viene più considerata come issue aperta da risolvere.

\subsection{Archiviazione}

Solo gli amministratori possono archiviare una issue. Una issue archiviata non viene mostrata nella lista principale, ma resta accessibile da una sezione dedicata. Questa scelta permette di non eliminare dati utili e di conservare la tracciabilità delle segnalazioni.

\section{Testabilità}

\path{backend/BugBoard26.Tests/IssueDomainServiceTests.cs} verifica regole pure di ricerca, carico e autorizzazione. I test di integrazione avviano \texttt{Program} tramite \path{WebApplicationFactory}, usano JWT ottenuti con il login reale, Npgsql e un PostgreSQL dedicato sulla porta 55432. Ogni caso crea un database temporaneo distinto; non usa il database di sviluppo né repository simulati.

\texttt{IssueStatusIntegrationTests} verifica risoluzione da parte dell'assegnatario con segnalatore distinto, date e notifica persistite, ADMIN non assegnatario, rifiuto di USER non assegnatario e READONLY, ripetizione di \texttt{Resolved} senza nuove date/notifiche, 401 senza token e 404 per issue assente. \texttt{NotificationsIntegrationTests} verifica elenco personale ordinato, lettura persistita per USER/ADMIN/READONLY, rifiuto di notifiche altrui, 401, 404 ed elenco vuoto. Il successo di questi test descrive il comportamento attuale, non chiarisce da solo RF-17.

La riapertura dopo \texttt{RESOLVED}, una seconda risoluzione e la ripetizione del PATCH read non hanno casi dedicati in questi due file: restano nella checklist manuale. Esiti realmente eseguiti e limiti sono registrati in \path{Documentazione}/\texttt{Documentazione finale}/\path{readme.md}; la compilazione LaTeX non è una prova applicativa.

\section{Limiti e verifiche dopo il merge}

\begin{itemize}
    \item Upload immagini non implementato: \texttt{ImagePath} è presente nel modello, ma non esiste un endpoint di upload né un campo corrispondente nel DTO di creazione.
    \item Gestione \texttt{Duplicate} tramite PATCH status e \texttt{ResolvedAt} nel percorso duplicate ancora da ricontrollare dopo il merge del collega.
    \item RF-17 da chiarire sulla lettura delle proprie notifiche per READONLY; nessuna eccezione viene aggiunta al requisito.
    \item Diagrammi iniziali diversi dal cambio stato ancora da allineare come indicato nelle relative sezioni; notifiche senza email o aggiornamento realtime.
\end{itemize}

\section{Conclusioni}

La progettazione proposta divide BugBoard26 in componenti indipendenti e con responsabilità chiare. Il frontend Angular si occupa della presentazione, il backend ASP.NET Core contiene la logica applicativa e PostgreSQL gestisce la persistenza dei dati.

La struttura a livelli adottata rende il sistema più ordinato, testabile ed estendibile. Le scelte di design sono coerenti con le funzionalità assegnate e con il vincolo di realizzare un sistema distribuito con frontend e backend separati.
